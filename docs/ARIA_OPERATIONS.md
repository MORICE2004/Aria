# ARIA — Operations Runbook

What to do when something is wrong, and what to do regularly so it isn't.

Written 2026-08-16. Everything here has been run against the real system.

---

## Is ARIA healthy?

Two endpoints, answering deliberately different questions:

```bash
curl -s localhost:8000/health
```
Is the API process alive? Cheap, never fails because a dependency is down,
never rate limited. If this fails, the process is gone — restart it.

```bash
curl -s localhost:8000/ready
```
Can ARIA actually work? Checks database, schema revision, local model,
background workers, and auth. Each reports independently, so
"database down" never hides "model also down".

`auth` reporting `ok: false` does **not** make ARIA unready. It is a posture
warning: she keeps working, but refuses to send messages unattended.

---

## Daily / weekly

**Back up the database.** ARIA holds things that exist nowhere else — her
memory of you, your learned writing voice, your message history. Postgres in
a Docker volume is durable right up until someone runs `docker compose down -v`.

```bash
./scripts/backup-db.ps1
```

Keeps the last 14 by default (`-Keep 30` to change). The script refuses to
write a dump under 1 KB, because a backup you cannot restore is worse than
none — you stop worrying about it.

**Check the Activity page.** Review autonomous replies. Silence teaches ARIA
nothing: an unreviewed response stays `none` forever and is excluded from her
correction rate, deliberately, so she cannot grow confident because you
stopped paying attention.

## Schema changes

ARIA uses Alembic. `create_all` was removed from the Postgres path because it
was a proven liability: it creates missing *tables* but never alters existing
ones, so a new column was invisible to it — the app booted fine and returned
500 on the first query selecting that column. Tests stayed green because
SQLite builds every table from scratch.

```bash
cd apps/api

# after changing src/models.py
.venv/Scripts/alembic revision --autogenerate -m "what changed"

# ALWAYS read the generated file before applying it. Autogenerate proposes
# drops as confidently as it proposes adds.
.venv/Scripts/alembic upgrade head

# confirm models and schema now agree
.venv/Scripts/alembic check
```

Migrations also run automatically at API startup, so a normal restart applies
anything pending.

**Back up before migrating.** Always:
```bash
./scripts/backup-db.ps1 -Label before-migration
```

**Rolling back:**
```bash
.venv/Scripts/alembic downgrade -1
```
Autogenerated downgrades drop columns, which destroys data. Restore from the
backup instead unless you have read the downgrade and know it is safe.

## Something is wrong

### Messages are arriving but nothing happens

Check the queue:
```bash
curl -s localhost:8000/whatsapp/queue
```

- `pending` climbing with `backlog_seconds` growing → the worker is not
  running or the model is down. Check `/ready`.
- `dead` above zero → messages exhausted their retries. They are **not lost**:
  ```bash
  curl -s "localhost:8000/whatsapp/queue/items?status=dead"
  curl -s -X POST localhost:8000/whatsapp/queue/<id>/retry
  ```

The proactive engine raises both of these on its own within five minutes; the
dead-letter check is the highest-value one in the system, because from the
sender's side an unhandled message just looks like you did not reply.

### ARIA is not replying to a contact she should

Ask her why, without changing anything:
```bash
curl -s -X POST localhost:8000/whatsapp/evaluate \
  -H 'Content-Type: application/json' \
  -d '{"handle":"john@s.whatsapp.net","body":"hey"}'
```
The response carries the decision and the reasons. Common causes, in the order
the engine checks them: emergency stop, pause, takeover, contact pause, risk
too high, category never autonomous, autonomy not enabled for that contact,
action not in their allowed list, **no ARIA_PASSWORD set**, communication
confidence below 0.70, or too many recent corrections.

### ARIA sent something she should not have

1. Emergency stop, from `/activity` or:
   ```bash
   curl -s -X POST localhost:8000/whatsapp/emergency-stop
   ```
   This blocks all outward messages, forces observe mode, and cancels anything
   already queued.
2. Correct the response on `/activity` so she learns from it.
3. If it is one contact, take over that conversation instead of stopping
   everything.
4. **The hardware-level stop:** unlink ARIA's sender device on your phone
   (WhatsApp → Settings → Linked Devices). She then physically cannot send,
   whatever her software believes. This is the one that still works if ARIA's
   code is wrong.

### The bridge is running but ARIA sees nothing

Messages are on disk, not lost:
```bash
ls apps/wa-bridge/spool/pending/
```
The bridge holds every message until ARIA acknowledges durability, retrying
with backoff. Start the API and they drain automatically. Anything in
`spool/dead/` needs a look but is still intact.

### The API will not start

If it exits complaining about security configuration, that is deliberate:
`ARIA_PASSWORD` is set while `SECRET_KEY` is still the published example
value. Tokens signed with it are forgeable by anyone who has read this repo,
so login would look like protection and provide none.

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```
Put that in `.env` as `SECRET_KEY`.

## Starting and stopping

```bash
./start-aria.ps1              # databases, API, dashboard
./start-whatsapp-bridge.ps1   # WhatsApp observer (read-only)
node apps/wa-bridge/sender.js # WhatsApp sender - only when you want autonomy
```

The sender is **not** started by the launcher. Observing is the default;
sending should require a deliberate act.

Stale uvicorn processes serve old settings and have repeatedly caused false
"wrong configuration" readings. Before verifying any config change:
```bash
taskkill //F //IM python.exe
```

## Verifying message durability yourself

Do not take it on trust — the three-phase check kills the API on purpose:

```bash
cd apps/wa-bridge
node live-outage-check.js phase1   # ARIA up: baseline delivery
# stop the API
node live-outage-check.js phase2   # messages must be HELD on disk
# start the API
node live-outage-check.js phase3   # they must all arrive
```

## What ARIA cannot do

Stated so it is not discovered as a surprise:

- **No web access.** No search provider is configured, so the research agent
  works over your own memory, documents and messages only. Every answer says
  so. Adding web search is one `SourceProvider` adapter plus a key.
- **No OCR.** A scanned PDF is refused with an explanation rather than
  ingested as empty.
- **No calendar integration.** Google Calendar OAuth was deferred.
- **Automating WhatsApp violates its Terms of Service.** Read-only is lower
  risk than sending; sending is higher. Use the demo number.
